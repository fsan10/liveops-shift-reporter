# AGENTS.md

## Project purpose
Build the live-stream operations data collection and reporting system described in the project brief. The system connects to the active Douyin Compass browser through Playwright/CDP in the Cloak Login test environment, extracts metrics from documented page APIs where available, captures the specified screenshots, sends reports to Feishu, and synchronizes rows to a Feishu Bitable.

## Working rules
- Keep the test profile and production browser modes separate. Resolve Cloak's current endpoint through its local MCP service; start the configured profile only when it is not running. Never stop or restart an already-running profile.
- Discover the room only when no schedule/handoff room is bound, or after a manually saved interruption unlocks the old room. Keep using the bound room ID across normal handoffs and midnight, including after it has ended; do not require it to remain in the realtime list. Persist confirmed identity independently of metric completeness. Discovery uses fully paginated history over the actual business-date interval, including both dates of a cross-midnight shift; never choose another room just because it is currently live. Reload the matching live-detail tab for every funnel screenshot; reuse matching professional, basic, and Qianchuan dashboards without reloading. Await fresh valid metric responses and rendered cards before screenshots; Qianchuan must select 全域支付数据 and use its payment overview dataset. Direct routes take priority; use the documented DOM clicks only after a direct route fails.
- Prefer page network APIs and structured response payloads for metrics. Use DOM extraction only when no stable API response is available; capture the conversion funnel as an element screenshot and other report views as full-page screenshots.
- Treat page/API values as source data. Keep derived metrics and their formulas explicit, versioned, and covered by tests.
- Normal company shifts use actual cumulative capture snapshots as operational handoffs, with the first host starting at zero and later hosts subtracting the previous final snapshot of the same room/account. Normal navigation, settle and screenshot latency is recorded, not classified as a collection failure. Session interruptions are marked manually on the schedule row: capture and persist the old room fragment immediately, start the restarted room at zero, merge saved fragments at shift end, and hand only the newest room's final snapshot to the next host. Repeating a mark replaces the same room fragment. Use fully paginated history and confirmed detail timestamps to locate manually interrupted rooms; never automatically merge unmarked sessions or subtract across rooms/accounts. Counter increments are not interval/cross-session unique users; average/rate cards retain their explicitly disclosed snapshot scope. Provisional/interruption captures cannot become the following host's end baseline.
- Keep report and discovery browser tabs open after capture, including on failure; remove only the collector's response listeners. Reuse matching tabs, reload the live-detail funnel, and await fresh API/card data on retained realtime dashboards.
- If a retained Qianchuan tab still cannot produce fresh valid payment data after its retry, preserve it and initialize one new tab for the same room/account. Verify fresh API values against rendered payment cards and prefer the newer matching tab on the next run; do not reload or close the operator's existing dashboard.
- Store credentials and session endpoints in environment variables or encrypted settings. Never commit tokens, cookies, CDP endpoints, screenshots containing merchant data, or `.env` files.
- When sanitizing or publishing to GitHub, remove real personnel names and roster data from tracked source, fixtures, and documentation, while preserving generic color palettes, automatic color assignment, and color regression tests. Keep the operator's local roster/settings and browser color cache unchanged; exclude private runtime data from Git instead of deleting it.
- Keep scheduled and manual runs idempotent, auditable, and safe to retry. Record per-page, per-screenshot, Feishu, and Bitable outcomes.
- Share actual runs and unexecuted terminal screenshot plans between the collection history and overview queue. Deduplicate plans linked to real runs; label unexecuted entries by their planned timestamp without inventing execution logs or captures.
- Control anchor summary collection, roster-hour detail collection/screenshots, and anchor shift screenshots independently. Hourly work belongs to enabled roster shifts, never to live-start clocks. Split one hour while at least two hours remain; merge the remainder shorter than two hours into the final period. Store hourly metrics and cumulative baselines separately from anchor handoffs. Never use an already-subtracted hourly increment as the next baseline or let an hourly placeholder become an anchor handoff. Disabling anchor screenshots must not disable either data chain.
- Preserve valid hourly end cumulative snapshots independently of delta completeness and integration status, including across restarts and host boundaries. A missing starting baseline must not discard a valid ending snapshot or force the following hour to fail. Missing/invalid ending snapshots and unmarked room/account changes must never create fabricated baselines.
- Anchor screenshots use the anchor Feishu chat and hourly screenshots use the separately configured business chat; never fall back between these destinations. Merge coincident planned timestamps only for the same confirmed room/account, including the shift settle delay, and fan out saved images with separate delivery receipts. At the shared shift end, derive summary and last-period metrics from the same capture with their own baselines. Synchronize hourly details as native Bitable child records using self-links, stable source keys and a dedicated hierarchy view. Keep the summary as the only top-level aggregate, and delete remote cold children before parents. Preserve roster-hour plans, cumulative snapshots and delivery state across restarts; do not fabricate missed historical images or automatically resend deliveries whose outcome is uncertain.
- Compass discovery must read response bodies as they arrive, discard responses from previous document navigations, and wait for valid realtime/history payloads through SSO transitions. Retry discovery at most once; preserve tabs for human recovery. Terminal collection/data/page/integration failures must send one audited Feishu group alert per run, with safe diagnosis and recovery instructions; notification failure must preserve the original error.
- Roster dates before today in Asia/Shanghai are read-only in both views and mutation APIs. List history is collapsed by default; calendar history stays visible in gray. Highlight the entire current date and reveal it when opening the roster or switching views. Automatic fill/reset may change only today and future dates; incomplete local drafts must never break roster rendering or create historical schedules.
- Preserve unrelated user files and browser state. Do not change account, shop, or live-room selection unless the configured schedule requires it.
- Use the repository's virtual environment for Python development. Keep setup and operation documented for Windows/PowerShell.
- Run focused validation after changes; report what was and was not verified against the live merchant portal.
- Stop every project test service started by Codex as soon as validation finishes, including its child processes, and verify that its listening port is released before ending the task. Do not leave the backend running; the operator starts it manually. Preserve services that were already running before the test.

- Keep secrets out of source control; add new persisted configuration fields to the settings schema and operator documentation.
