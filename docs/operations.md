# 运维说明

## 主播汇总与排班小时明细

自动调度保留三个开关，保存后作用于后续任务：

| 配置键 | 默认 | 功能 |
| --- | --- | --- |
| `data_collection_enabled` | `true` | 按主播排班结束时间采集整班指标，维护主播交接基线并同步汇总 |
| `hourly_screenshot_enabled` | `false` | 按主播排班分段，采集小时指标和独立累计基线，截图发送业务群并同步小时子记录 |
| `anchor_screenshot_enabled` | `true` | 在主播排班结束时截图并发送主播群 |

主播自行截图、业务看小时数据时，推荐设置为开、开、关。小时功能自身包含数据和截图，不依赖主播汇总开关；关闭主播截图不影响两类数据。没有启用的排班就不会生成小时任务，不再根据实际开播时间计时。

### 分段和基线

- 从排班开始计算，剩余时间不少于 2 小时就划出 1 小时；剩余不足 2 小时直接作为末段。07:00–11:30 的结束点为 08:00、09:00、10:00、11:30，末段 1.5 小时，11:00 不额外截图。08:00–12:00 则在 09:00、10:00、11:00、12:00 各采集一次。短于 2 小时的班次只有一个完整段。
- 所有时间按 Asia/Shanghai，跨午夜继续原排班，小时子记录业务日期归属父排班日期。各段结束后沿用现有等待秒数，正常页面、截图和同步延迟保留实际时间。
- 主播汇总仍从上一主播最终快照交接，当日首班从 0 开始。小时明细的初始基线另存 `shift_hour_states`；可从上一班最终小时累计快照初始化，否则复制原主播起始基线，两套存储互不覆盖。
- 每段都用结束时的累计快照减本段起始累计快照。例如累计 GMV 为 100、250、450、900，则四段 GMV 为 100、150、200、450，最后 1.5 小时的每小时成交额为 300。下一段保存 250 这样的累计值作为基线，不能保存 150 这样的已计算增量继续相减。
- 小时指标写入 `shift_hour_details`，整班指标仍写入 `shift_reports`。小时临时父容器标记为汇总待结算，不能成为下一位主播的交接基线。主播汇总不通过小时行相加来替代独立计算。
- 人数为同场累计计数净增量，不是区间独立去重人数；GPM、互动率和停留保留段末页面卡片口径。累计回退、缺少基线、跨账号或未手动标记的换场不会伪装为 0。
- 中断仍在排班行手动保存旧场片段；小时段只合并其区间内已保存的片段，下一小时只继承新场结束累计快照。只开小时功能时也可保存中断片段，不覆盖主播汇总基线。
- 错过结束点与等待时间后超过 5 分钟、且未采集过的小时段记为漏采，不用当前累计值补造历史小时。后一段若没有相邻段的累计结束快照，会明确缺失；取得本次有效快照后，下一段仍可恢复。已采集的日期、时段禁止修改，以免破坏区间归属。
- 小时段缺少起始基线、指标不完整或群发送/多维表格同步异常，不会丢弃已取得的有效结束累计快照。下一小时或下一主播首个小时优先使用这份小时链快照；小时明细显示“结束累计快照已保存”。没有取得有效快照时不制造基线，未标记换场和账户不符也不能强行相减。

### 截图与群

- 末段与主播任务结束点相同，只执行一次页面采集和截图；同一套原始累计快照分别按整班与末段基线计算。主播群和业务群分别生成文案及回执，任一截图开关关闭只停止对应群的截图发送。
- `feishu_chat_id` 是主播群；`feishu_hourly_chat_id` 是业务群，互不回退。两个群共用应用凭证，机器人需分别加入。截图模块仍由采集脚本页选择，漏斗元素截图、其余整页截图。
- 小时文案支持 `{host_name}`、`{promoter}`、`{hour_index}`、`{start_time}`、`{end_time}`、`{duration_hours}`、`{gmv}`、`{overall_amount}`、`{overall_roi}`、`{shop_name}`、`{live_room_id}`、`{planned_time}`、`{captured_time}`。原系统默认开播文案自动转成排班段文案，自定义文案保留。
- 重启保留小时计划、累计快照及逐群送达状态。采集记录可仅补发未成功的群，成功群不重复发送；超时或退出时送达不确定的消息先人工核实，不自动重发。
- 漏拍、跳过等未执行计划与实际运行记录统一显示在“采集记录”和总览“采集队列”，按实际运行时间或计划时点排序；已关联运行的截图计划不重复显示。未执行计划标明计划时点，详情不会伪装出实际开始时间、日志或历史截图。系统配置只保留配置项，下一次小时任务在总览队列标题下与“最近的自动采集与人工执行”每 6.5 秒轮播，鼠标悬停暂停，提示框可同时查看两条信息。

### 数据明细与多维表格

- 数据明细页一行对应一个主播排班，点击行或左侧段次按钮可滑动展开小时明细。默认折叠，打开的明细自动更新；汇总与小时指标不会在总览中重复相加。缺失、漏采和待采集各自标记，可查看独立起始及结束 GMV 累计值。
- 飞书使用同一张表的原生父子记录：主播汇总为父记录，小时行为子记录。子记录独立填写业务日期、主播、投手、时段及指标，因为飞书不会继承父行字段。
- `bitable_parent_field` 默认“父记录”，须为指向当前表的单向关联字段。缺少时自动创建，已有同名不兼容字段不会覆盖。`bitable_hourly_view_id` 可指定层级表格视图；留空复用已有的第一个表格视图，配置父子层级，不重复建同内容视图。视图不是数据表的副本，删除视图不等于删除记录；已有人工视图不自动删除。
- 机器人需要数据表、字段、视图和记录编辑权限。`bitable_sync_key_field` 默认 SourceID，不存在时创建文本列，同名非文本字段报错；父键为 shift-ID，子键包含排班 ID、段次和口径版本。重试前按键查找远端，避免本地丢失回执或人工删除远端记录后产生错误引用。
- 汇总待结束时可先建立父容器并同步已采集小时。父行没有整班指标时留空，结束后原位更新。小时同步异常不会丢失本地原始累计快照。同步工具位于数据明细页顶部，按日期筛选范围同步全部页的汇总和小时明细，不重新打开商家页面或截图。
- 升级由操作员重启后台，新表自动创建，原排班、基线、报告、群配置和凭证保留。旧版按开播时间的小时记录仅供历史审计，不参与新的小时链。
- 配置页面依据当前后台返回的字段保存，只提交已修改值，空密钥继续保留原凭证。页面比后台更新时，未支持的新配置置灰并提示，修改业务群不会被新增字段阻断。若重启后仍不支持新字段，核对实际监听端口的进程启动时间，确认替换的是正在服务的实例。

接口依据：飞书开放平台《多维表格中添加子记录》：https://open.feishu.cn/document/docs/bitable-v1/app-table-record/add-a-sub-record-in-a-base-table 。

## 月表与范围同步

- 飞书保留当前自然月及前三个月。例如 2026-11 的热范围为 2026-08 至 2026-11；跨午夜的小时子记录仍归属父排班业务日期对应的月表。筛选可查看所有本地历史，超出热范围不自动重建远端冷表。
- 首次启用按月路由时建立当月新表，保留原有表及数据；名称包含业务年月和持久化管理编号。新月表按字段映射创建列，仅有一个父子记录表格视图。首次迁移历史数据可在数据明细选择本月或近四个月，执行全量刷新。
- 配置 `bitable_table_id` 自动显示当前月目标，留空可自动建表。手动保存新 ID 只覆盖当前自然月；次月自动建立新目标，历史月份重试仍进入其已登记月表，不把当前 UI 目标改回旧月。换表默认清除旧层级视图 ID；可同时显式设置新视图 ID。更换 app_token 而未提供新 table_id 时清空旧表绑定，避免跨多维表格写错目标。
- `bitable_table_month`、`bitable_table_mode` 为系统维护的只读设置。月表路由和创建凭据记录在 `bitable_month_tables`；远端记录 ID、内容指纹和同步状态按目标表及 SourceID 隔离存入 `bitable_sync_receipts`。切换目标不沿用其他表的记录 ID。
- 自动清理仅删除本地登记为机器人创建且超过热范围的整张月表。人工创建、未知来源、未登记的表永久受保护；不会通过名称猜测所有权。当前仍在使用或被近四个月目标引用的表也受保护。删除失败保留登记并重试；本地排班、累计快照、报表和小时明细不删除。
- 建表前持久化唯一名称。网络超时或结果不完整后，重试先完整枚举远端表并找回；若结果仍待确认则停止再次创建，提示在飞书核对或人工指定 table_id，避免建重复月表。
- 数据明细默认当天，日期范围筛选包含起止日期，导出 CSV 与同步使用同一范围。点击“同步到飞书”选择：**增量同步**仅补充新增、内容变化或失败/不完整记录；**全量刷新**强制把范围内全部本地汇总与小时明细按 SourceID 重写或补回，不清空其他日期、人工行或整张表。鼠标悬浮选项可查看解释。
- 同步是后台任务，采集记录展示“飞书范围同步”、进度与错误；同一时间只接受一个范围任务。同步失败仍可增量重试。不会重新采集、截图或发送已有群报告；原群送达回执保持不变。
- 采集记录默认当天，可选择任务时间或完成时间，并组合日期时间范围、任务类型、状态。漏拍计划按计划时点参与任务时间筛选，没有完成时间，不参与完成时间筛选。筛选先于计数和分页，显示时间均为北京时间。
- 更新后由操作员重启直播运营后台，再刷新页面。新表自动建库；后台未加载新接口时，页面禁用新范围功能并提示，避免把旧接口忽略筛选参数的结果显示为筛选成功。

## Excel 排班导入

在排班管理工具栏点击“导入排班”，下载模板、替换示例内容并通过 Ant Design 上传按钮选择文件，点击“预览并校验”，核对逐行结果后“确认导入”。导入使用文件内的实际日期，不受页面当前月份限制；完成后刷新当前月份，其他月份通过月份切换查看。窗口关闭或文件改变后，需重新预览。

- 支持 `.xlsx` 和本系统导出的 `.csv`（UTF-8 或 GB18030），不超过 5 MB、2000 行。旧版 `.xls` 须先另存为 `.xlsx`；Excel 只读取第一张工作表，不读取说明页或执行公式。请将公式粘贴为值。
- 第一行表头必填“日期、时段、主播”，可选“星期、投手、休息、日常拍摄”。支持用“开始时间、结束时间”两列替代“时段”；“运营”列兼容映射为投手。日期填写完整年月日，支持 Excel 日期单元格；独立的开始/结束列支持 Excel 时间单元格。日期合并或同日后续行留空时继承上一行日期。
- 时段示例 `07:00-11:30`、跨午夜 `20:30-01:00`，跨午夜班次归属开始日期。只有休息/拍摄备注时可将主播和时段留空。新增班次默认启用，沿用当前店铺、直播间及千川账户默认配置，后续调度遵循现有采集开关和时间规则；导入接口不直接执行采集。
- 历史日期按 Asia/Shanghai 跳过并列明行号。日期、起止时间、主播和投手完全相同的班次跳过，不修改原启停状态、绑定场次、报告及基线；文件内重复班次同样跳过。非空备注可补充到空备注，已有不同备注视为冲突，空备注不清除已有内容。
- 沿用手工排班的重叠校验（包括跨午夜及停用班次）和启用班次的同日主播唯一规则。任何格式错误或业务冲突均阻止整批写入；预览不持久化，确认时重新检查最新排班。重复提交不会重复新增。
- 接口：`GET /api/schedules/import-template` 下载模板；`POST /api/schedules/import?preview=true` 使用 multipart 文件字段 `file` 预览；`preview=false` 确认导入。响应提供原始行号、逐行状态、错误原因、新增班次/备注计数；确认失败返回 409，文件格式错误返回 422。文件解析完成后不保留原始上传文件。

升级时在项目虚拟环境执行 `.\.venv\Scripts\python.exe -m pip install -e ".[dev]"` 安装 Excel 读取依赖，再由操作员重启后台、刷新页面。无需迁移现有排班数据。

## Cloak Login 测试模式

1. 后台按 profile 名称或可选 ID 调用本机 Cloak MCP `list_active`；若目标未运行，调用 `start_profile`。每次均使用实时返回的 CDP 地址。
2. 采集前复用抖店标签打开首页，登录态失效时调用复用的抖店邮箱登录/店铺选择状态机。可见滑块由人工处理，后台向配置的飞书负责人发送 @ 提醒并等待，不读取或绕过验证码。
3. 罗盘直播列表的实时接口返回本次 `live_room_id`。当天排班按此 ID 生成详情、专业版、基础版和千川最短直达 URL。详情页每次重新加载后截取成交转化漏斗；专业版、基础版和千川大屏复用匹配直播间的标签，不重新加载页面。新直播间或路由不匹配时才导航，直达失败才执行配置的 DOM 路径。
4. 千川顶部指标卡必须选中“全域支付数据”；接口必须返回同口径的消耗、券、补贴、曝光、GPM 和顶部成交/ROI 卡片，截图前核对 7 个卡片数值与该响应一致。已结束的直播可能停止自动轮询，专业版/基础版通过浏览器内原页面 GET 接口补取数据，由页面 SDK 生成新签名；千川重新选择指标卡口径触发原生接口更新，不重载大屏。接口未就绪自动重试一次；超过等待上限保留具体中文缺失原因，不把空响应或 `--` 当作完成。
5. 截图模式保持成交转化漏斗为元素截图，其余模块为整页截图。罗盘截图前检查页面视口；小于 1280×720 时，临时扩展到可用屏幕尺寸（最大 1920×1080）后截图，并恢复原视口，不改动 Cloak 窗口大小。千川保留现有整页截图路径。

## Playwright 原生浏览器生产模式

切换到“原生浏览器”后，后台在 `NATIVE_USER_DATA_DIR` 创建持久化 Chromium profile。首次启动需人工登录平台并确认账户、店铺与广告账户；后续任务复用该 profile。`locale`、`timezone_id`、视口、缩放倍率和浏览器路径可在配置页修改。浏览器实际支持的指纹范围取决于 Playwright/Chromium；Cloak 专属的 Canvas、WebGL 或字体伪装不会自动迁移。

## 飞书配置

使用企业自建应用机器人模式，不是仅有 webhook 的自定义机器人。填写 App ID、App Secret、目标群 Chat ID，以及多维表格 app_token、table_id。机器人必须启用并加入群聊；应用需获准发送消息，并开通 `im:resource:upload` 或 `im:resource` 应用身份权限以上传图片；对目标多维表格还需有查看、编辑权限。报告按“直播数据报告：”标题、图片、说明文字的顺序发送。系统先上传截图获得 `image_key`，再发送图文消息，所以仅验证文本测试消息不能证明截图链路可用。多维表格字段名通过字段映射与表格中的实际列名对应。

新建排班只需填写日期、主播和开始/结束时间。当天排班的直播间 ID 会从罗盘实时列表自动发现；千川账户 ID 沿用系统配置的默认账户，不需要在每个排班重复填写。人工采集只允许当天排班，历史和未来排班会在任务入队前被拒绝；定时任务仍按排班结束时间运行。

排班管理复用 2026 年 10 月原型的日期卡片、月历、人员弹层、时段模板、休息/拍摄编辑、侧栏统计和撤销操作。原型中的“运营”在项目中统一作为“投手”，与主播一起保存在班次中。新增班次先出现空行，补全时段和主播后自动写入服务端；未补全的空行保存在当前浏览器。操作列提供开始采集、标记中断、停用/启用、删除，列表中的班次修改直接点击对应单元格；月历点击班次或新增空班次后打开“时段、主播、投手”菜单，悬浮或点击选项展开二级设置。时段支持开始/结束时间输入与常用模板，主播和投手支持候选选择、搜索或输入姓名；设置后自动保存，按 Escape 或点击外部关闭菜单。自动排班按目标日期的星期轮换 2026 年 10 月模板，并复制休息和拍摄备注；已有内容时不会覆盖。点击“恢复原始”仅恢复当前月份今天及未来日期的模板排班；待替换日期存在采集报告或记录时拒绝替换，以保留审计记录。原“从罗盘导入轮班”入口和接口已移除。

排班日期按 `Asia/Shanghai` 判断。今天之前的日期只读，不能新增、编辑、启停或删除班次，也不能修改休息/拍摄备注；后端接口同步拒绝这些操作。列表将历史日期默认折叠到“历史排班”，展开后覆盖半透明灰色蒙版并禁止交互，保留原有人员颜色；月历完整显示历史日期并使用同样的蒙版。今天的整个日期区域有浅蓝细框及向外扩散的柔光。首次打开、重新进入排班管理或切换列表/月历时回到本月并自动将今天显示在固定工具栏下方；浏览其他月份可继续使用月份按钮。自动排班及恢复模板跳过历史日期，保留历史班次和备注。页面加载时清除 2026 年 10 月 1 日误加、未保存且时段/主播/投手均为空的本地班次；已保存班次和其他草稿保留。历史草稿不会自动写入后端，也不会导致列表渲染失败。修改程序后由操作员重启后台以使后端日期限制生效；刷新页面可加载新的前端。

公开 GitHub 提交应排除真实人员名单、实际班表、数据库和浏览器缓存，但必须保留通用调色板、自动分色逻辑和配色回归测试；脱敏只清理拟提交的代码及示例，不清空本机业务数据。人员配色使用通用的多色调色板，与真实姓名配置分离；已分配颜色缓存在当前浏览器，列表、月历、侧栏和人员菜单保持一致，刷新、切换月份或调整名单不重新分配。没有缓存的新人员自动补色，颜色缓存损坏或浏览器禁用存储时仍可正常显示。侧栏“主播班次统计”和“投手班次统计”的设置按钮管理可选人员。公开安装的默认人员名单为空，需要在系统配置中添加当前团队成员。名单分别保存在系统配置 `roster_anchor_pool` 与 `roster_promoter_pool`，删除人员仅移出可选名单，不改已有班次。排班视图只使用内部滚动条，日期工具栏和视图切换栏固定在顶部；排班连接及保存状态与服务状态在主界面顶部胶囊轮播显示。若旧服务尚未重启，新名单暂存当前浏览器，重启后自动同步到配置。

## 运行和恢复

- 罗盘可能短暂显示未登录，随后通过抖店登录态完成自动跳转。抖店登录正常不等于罗盘接口已经就绪。场次发现收到响应时立即读取正文，页面导航后丢弃旧文档响应；只有同一文档的实时和历史列表接口均有效、罗盘路由稳定后才继续。每次等待上限沿用 `PORTAL_TIMEOUT_MS`（默认 45 秒），超时只重新打开一次直播列表，不重启 profile、不改变账号或绑定场次。失败时保留标签，人工检查登录、验证及权限后再采集。
- 手动/定时任务彻底失败、字段或页面缺失、群报告发送或多维表格同步失败时，机器人向已配置的群发送“直播运营异常提醒”，包含北京时间、排班/主播、失败环节、原因判断、处理建议和运行编号；沿用 `feishu_alert_open_id` 可 @ 负责人。原因判断是根据错误类别生成的提示，详细原始错误仍在后台。只因班次未结束产生的临时快照不提醒。同一运行只尝试一次终态提醒，重试采集是新的运行；滑块等待期间的人工接手提醒仍单独保留。
- 运行详情的 `exception_alert` 和“异常提醒”步骤保存发送状态及成功消息 ID；未配置或发送失败也留痕，原始采集错误不被覆盖。飞书业务返回成功且存在消息 ID 才标记送达。网络超时可能无法确认消息是否到群，因此不自动重发提醒；机器人或网络不可用时只能在后台看到提醒失败。先检查飞书配置/权限/网络。已经保存的数据可按后台实际结果重试同步，避免重复发送成功的群报告。修改程序后需要操作员重启后台，新异常提醒才会用于后续任务。
- 采集记录页记录每次手动或定时触发，展示开始与完成时间、逐步运行日志、缺失指标和错误摘要。数据明细与采集记录分页默认每页 20 条，页数可单独记忆。
- 首次采集发现并绑定直播场次，之后优先使用排班已绑定的 ID，其次使用上一班最终快照的 ID；正常停播或跨午夜不会解除绑定，也不会因另一个场次在线而自动切换。场次身份在详情接口确认后独立保存，其他指标缺失不会丢失场次。`live_author_id` 可固定账号；多账号歧义或接口失败停止归属。
- 正常班次按实际快照交接：第一位基线为零，后续同场累计值减上一位最终快照。导航、等待结算及截图引起的正常延迟仅记录实际时间，不因晚于排班结束几十秒而 partial。真实接口缺失、无上一位基线、账户不匹配或累计回退仍需处理。
- 断播续播时，在该排班行点击“标记中断”，选择中断时间并点击“标记并采集”。立即保存绑定的旧场片段，成功保存后才允许发现新场；不提前替换完整报告或向下一班传基线。班次结束时，新场从零开始，与旧场增量合并；下一位只继承新场结束快照。多次断播需分别标记，同场重试替换原片段且不改绑已确认的新场。重新发现按实际班次日期范围查询全部历史分页，包括跨天的前一天；多个未保存场次必须分别标记，不能自动跳到最新场。没有续播时只结算已保存旧场片段。普通下班停播无需标记中断。
- 成交人数、点击人数、场观、增粉为同场累计净增量；跨场相加不做联合去重。GPM、互动率、停留使用最后一场结束时的页面卡片，各场原值见详情。这些卡片不是跨场平均指标。当天最后一个排班时段完成后，日曝光按直播间 ID 去重，取当天每场最新的直播间整体曝光并求和，然后回填当天所有已生成时段并同步多维表格；同一直播间跨多个时段只计一次，手动标记断播后的不同直播间分别计入。缺少任一场的有效最终快照时整日留空并注明原因，不用时段曝光差分代替。完整口径见 data-sources.md。
- `shift_interruptions` 持久保存中断时间、room、广告账户、快照、原始响应和截图；程序重启后继续合并。完整报告按同一排班更新，不重复累加；临时报告在结束时重新结算且不能作下一班基线。
- 截图后保留详情、专业版、基础版、千川和直播列表标签页，包括页面失败时。下一次复用同场标签，详情页刷新，实时大屏等待新的有效接口与已渲染卡片，不重载匹配大屏。只移除本次响应监听器。
- 千川旧标签在停播后可能保留卡片但不能产生新响应。切换全域支付并重试仍超时时，保留原标签，额外初始化一次相同直播间和广告账户的页面；取得新接口且卡片数值一致才继续截图。下一次优先复用这个较新的同场标签，不自动关闭旧页。
- 修改程序后由操作员重启后台，启动会创建中断记录表并保留原排班/报告。已存在的旧自动分段报告保留旧口径；本次不会用晚到的最新整场累计值覆盖历史班次。
